# Builder

## Problem

A location is not one value. It has a name and one or more zones. Every zone
has a name, two thresholds and a schedule.

Passing all of that to one constructor would be hard to read. Some rules also
only make sense once every part is there. You cannot check that zone names are
unique until you have all the zones.

## Solution

Add the parts one at a time, then check them all at the end.

```python
config = (
    LocationConfigBuilder()
    .with_location_name("Lab Site A")
    .add_zone("Bench 1", 0.2, 0.45, {"watering": "08:00"})
    .add_zone("Bench 2", 0.25, 0.5)
    .build()
)
```

Each method gives the builder back, so the calls can be chained. Nothing is
checked while the parts go in. `build()` runs every rule. It either returns a
finished `LocationConfig` or raises `ConfigurationError`.

## Where validation lives

In `build()`, in the domain layer. Not in the router, and not in the database.

So an invalid config is rejected before anything is written. The rules: the
location name must not be empty, there must be at least one zone, zone names
must be unique inside one location, thresholds must be between 0.0 and 1.0, and
low must be below high.

`validate_zone_fields()` keeps the zone rules on their own. Adding or editing a
zone on a saved location must not rebuild the whole location, but it still has
to follow the same rules.

## Why this is Builder and not a factory

Factory Method picks which one thing to make. Abstract Factory picks which
matching set to make. Both decide a type and hand it back in one call.

Builder puts one complicated thing together in steps. The caller decides what
goes in, and the number of zones is not known ahead of time. There is also a
checking step at the end, which neither factory has.

## Why `location_id` and not `greenhouse_id`

The product is a smart greenhouse, but the thing in the database is a location.
One install can have several locations, and later phases join on this column.
The name should say what the row points at, not what the product is called.

## Why device assignment is not a builder method

A zone has no id until the config is saved, so there is nothing for a device to
point at while the builder runs. The devices also already exist from Phases 2
and 3, so they are not part of building a location.

Placement is a separate update through `ZoneAssignmentService`, after the zone
row exists. Moving a device never rebuilds its location. The service copies
`location_id` from the zone in the same write, so the two columns cannot
disagree.

## Where to look

| File | Role |
|------|------|
| `backend/src/domain/locations/entity.py` | `Location`, `Zone`, `LocationConfig` |
| `backend/src/domain/locations/config_builder.py` | the builder and the rules |
| `backend/src/domain/locations/errors.py` | `ConfigurationError` |
| `backend/src/application/locations/config_service.py` | builds, saves, and manages saved zones |
| `backend/src/application/locations/zone_assignment_service.py` | places devices, after the fact |
| `backend/src/infrastructure/persistence/location_repository.py` | one transaction per config |
| `backend/src/interfaces/api/locations.py` | routes; errors become 400 and 404 |
| `backend/tests/test_location_builder.py` | the rules, with no database |
